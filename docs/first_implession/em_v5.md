# Emther（EM Support System・エージェント駆動型EMサポートシステム） 構想・要件定義書（v5）

## 1. ビジョン
**「EMの関心を現場の効率化から、組織設計とミッションの実現へと引き上げる」**
本システムは、EMが本来向き合うべき「経営と現場を繋ぐミッション・ビジョンの策定」「人の介在戦略を含めた組織設計」「プロダクト開発組織の障害排除」に注力できるよう支援する。
AIは「前提となる組織の憲法」を深く理解した上で、複雑な事象をモデリングして選択肢を提示し、さらにEMとのインタラクティブな「壁打ち」を通じて思考を拡張する。最終的な決断と説明責任は人間（EM）が担う。

## 2. 要求（ビジネス・ユーザー要求）
1. **変動性・矛盾への対応:** 組織の時系列の変化や一時的な感情を「矛盾」としてエラーにするのではなく、時系列のログとして受け入れること。
2. **前提（ルール）とログ（揺らぎ）の分離と構造化:** 組織のMVVや体制等の「不動の前提」と、日々の「揺らぎのログ」を明確に区別し、AIが処理しやすい形で構造化して保持すること。
3. **情報の壁とセキュリティ:** ログ収集の困難さを前提とし、EM自身の入力（メモ等）を主な情報源としつつ、機密情報の秘匿化を行うこと。
4. **広範な専門性の網羅:** EMの4象限（プロダクト、プロセス、ピープル、テクノロジー）を適切にブレークダウンし、専門エージェントを配置すること。
5. **ブラックボックスの排除とインタラクティブ性:** AIの「思考過程の透明性」を保ちつつ、単なる一方向の提案ではなく、対話を通じた思考の壁打ち（Copilot）が可能であること。AIの「現在の行動」も可視化されること。
6. **Issueの双方向性と実行管理:** AI・人間の双方からIssueを起票でき、解決に向けた計画策定、実行追跡、ピボットまでをサポートすること。
7. **運用コストの最適化とコントロール (Human-in-the-Loop):** 高額なAPI課金を避けるためCLI実行エンジンを活用し、さらに「AIの自律実行の限界点（Yield）」を設け、無駄な推論コストを抑止しつつ人間が必ずコントロール権を握ること。

## 3. 要件（システム要件：8つのアーキテクチャの柱）

### 3.1 厳格に分離されたナレッジモデル（Core Context & Daily Logs）
* **Core Context (システム前提):** 組織のMVV、目標設定（OKR等）、組織体制。ツリー型ディレクトリ構造（例: `Strategy/`, `Teams/Team_A/`）および構造化フォーマット（JSON/YAML）で管理され、ハルシネーションを防ぐための「絶対の前提」としてプロンプトに静的注入される。
* **動的ローディング:** エージェントは対象Issueに関連するディレクトリのコンテキストのみを動的にロードし、推論のブレを防ぐ。
* **Daily Logs (イベント履歴):** 時系列データとしてのジャーナルメモやシステムログ。イベントソーシング的に管理され、ファクトと一時的な解釈を分離する。

### 3.2 前処理パイプラインを備えたハイブリッド・データ収集
* **ジャーナリング基盤:** EMが雑多なテキストを入力できる口を設ける。
* **軽量モデルによるIngestion（自動タグ付け）:** 入力された生データは、直ちに安価な軽量モデル（またはローカルLLM）を通過し、以下のメタデータを自動付与して検索・分類性を高める。
  * **タグ抽出:** `#モチベーション`, `#技術的負債` 等
  * **エンティティ抽出:** 人名（`@Aさん`）、プロジェクト名
  * **属性判定:** 緊急度スコア、感情のネガポジ判定
* **サニタイズ（秘匿化）:** 機密情報をパイプライン上でマスキングする。

### 3.3 階層型マルチエージェントアーキテクチャ
* **リードエージェント:** ユーザーとの対話窓口となり、全体を統括する。
* **専門エージェント群:** プロダクト、プロセス、ピープル、技術の各領域において自律的に分析し、リードエージェントへインサイトを提供する。

### 3.4 CLIサブプロセス実行エンジン（Cost-Efficient AI Engine）
* **非API型バックグラウンド処理:** エージェントの推論プロセスは、定額サブスクリプション範囲内で動作するシェルサブプロセス（`claude` コマンド等）を通じて実行。
* **対話ストリーム（REPL）連携:** Issue Workspaceでの「壁打ちチャット」時には、CLIのインタラクティブモードとWeb UIを標準入出力で直接ストリーム接続する。

### 3.5 思考過程の可視化とシグナル（Explainable AI & Status）
* **Agent Activity Stream:** CLIエージェントの標準出力（stdout）をダッシュボード上にストリーミング表示し、「今どのデータを読み、何を推論しているか」を可視化。
* **シンプル・ステータスインジケーター:** Activity Streamに加え、パッと見で状態がわかる信号機型のステータス（🟢 Active, 🟡 Waiting/Yield, ⚪️ Idle, 🔴 Error）を常設表示する。
* **構造化された提案:** 提案には必ず「結論」「参照ファクト」「判断ロジック」「棄却した代替案」を含める。
* **Team Vitals（組織バイタル）の三値表示:** チーム・組織の健全性は「良好（🟢）」「要注意/危険（🟡/🔴）」に加え、判定に必要なログ・メトリクスが一定期間存在しない場合は「評価不能（⚪️・情報不足）」として明示する。データ欠如を安易に「問題なし」側へフォールバックさせず、常に判断材料の有無そのものを可視化することを必須要件とする。判定閾値およびデータ欠如とみなす期間はCore Context（Rules_and_Constraints）側で定義し、各バイタルは根拠（参照期間・データソース、または不足しているデータの内容）を提示できること。

### 3.6 エージェントの自律実行境界とYield（一時停止）設計
AIの暴走と無駄なコストを防ぐためのステートマシン駆動制御。
* **トリガー（起動条件）:** イベント駆動（特定タグのジャーナル追加）、バッチ駆動（朝のサマリー）、人間駆動（直接の指示）。
* **Yield Point（コントロールの返却）:** エージェントは以下の状態に達すると処理を一時停止（🟡 Waiting）し、EMにアクションを促す。
  1. **解決策の選択:** 複数のアプローチ（A案・B案）を立案し、人間の「文脈（泥臭い判断）」に基づく決定を待つ時。
  2. **情報不足 (Missing Info):** 計画立案に不可欠な前提（例: 今期の予算枠）がナレッジベースに不足しており、人間からの提供が必要な時。

### 3.7 双方向のIssueトラッキング基盤
* AIによる異常検知（ドラフトIssue）と、EMの直感による起票（AIによる関連コンテキストの自動収集・エンリッチメント）を統合的に管理。

### 3.8 動的Issue実行管理とコラボレーティブ・プランニング
* **ズームイン / ズームアウト:** 抽象的な課題のタスク分解と、微細な課題からの根本原因発見をサポート。
* **壁打ちによるState更新:** EMとAIの対話（チャット）を通じて方針をブラッシュアップし、AIからのサジェストによってIssueの状態（タスクリストやロードマップ）を直接・動的に上書きできる仕組みを持つ。

## 4. 仕様概要（システムコンポーネント構成）

### 4.1 データ層（Knowledge & Context Base）
* **Core Context DB:** ツリー構造のディレクトリとファイル群（静的プロファイル）。
* **Daily Logs DB:** 軽量モデルによりタグ付け・エンティティ抽出済みの時系列ログ。

### 4.2 エージェント実行・オーケストレーション層
* **サブプロセスオーケストレータ:** CLIプロセスのライフサイクル制御、標準入出力ストリームのルーティング。
* **ステートマシン・コントローラ:** 各エージェントの「Active ⇔ Yield」の状態遷移を管理し、Yield時にはフロントエンドへ通知（プロンプト）を発行する。
* **コンテキスト分離注入機構:** 対象Issueに関連するCore Contextの内容のみを動的にロードする仕組み。

### 4.3 アプリケーション層（EM Dashboard UI）
1. **Organization Context:** ツリービュー型で組織の前提条件を構造的に管理する画面。
2. **ジャーナル・インプット:** 軽量モデルによる自動分類に対応したクイック入力ウィジェット。
3. **ダッシュボード（Home）:** トリアージ用Inbox、Agent Activity Stream、および信号機型ステータス表示。
4. **Issue Workspace:** 状態管理（左ペイン）とAIとの壁打ちチャット（右ペイン）を統合した協働空間。
