# Emther の思想・哲学

このドキュメントは、Emtherという製品が「何のために」「どういう考え方で」作られているかを一箇所にまとめた正本である。

個々の機能の実装仕様は `docs/` 内の各ドキュメント（`docs/knowledge_distillation.md` 等）やコードに委ねる。ここに書くのは、機能を追加・変更するときに立ち戻るための**変わりにくい前提**である。

このドキュメントは複数回のピボット（方向転換）を経て今の形に到達した内容の集約であり、過去の検討過程そのもの（各ピボット時点の課題認識・移行計画）は `docs/archive/` に残している。「なぜ今の形になったか」の経緯を追いたい場合はそちらを参照する。→ [変遷](#8-変遷1st4th-pivotの要約)

---

## 1. ビジョン

> **Emtherは、EMが考えるための場所。**

日々の観測情報・組織のコンテキスト・過去の出来事を蓄積し、AIがそれらを横断して

- 何が起きているか
- どう捉えられるか
- 他にどんな見方があるか
- 前提は妥当か
- 過去に何があったか
- 何を考えるべきか
- EM自身は何を学ぶべきか

を提示する。EM自身がIssueやタスクを細かく管理するのではなく、AIから得られた状況認識をもとに、**EMが判断し、コミュニケーションし、組織へ介入することを支援する。**

Emtherは、

- **EMの業務を自動化するAI** でも、
- **EMに正解を教えるAI** でもない。

目指すのは、**EMが組織・チーム・プロダクト・技術を多面的に理解し、より良い問いを立て、判断し、行動するための「思考の拡張環境」** である。

---

## 2. 基本コンセプト

> **EMは「記録する人」ではなく「考え、判断する人」。**
> **AIは「答えを出す人」ではなく「思い出させ、整理し、注意を向ける人」。**

Emtherを使うことで管理業務が増えてしまえば、「EMの業務を楽にするためのシステムが、Emtherを利用するための業務を生み出す」という逆転が起きる。これを避けるため、常に次の関係を保つ。

```text
EMの考え
  ↓
AIが複数の哲学レンズで見る
  ↓
EMが見ていなかった視点を発見
  ↓
EMの思考を広げる
```

単に「EMの考えをAIが整理する」だけの増幅関係にはしない。AIの役割は「問題の解決」だけでなく「問題設定の改善」を支援することにも及ぶ。「どう解決するか」だけでなく、**「そもそも何を問題として捉えるべきか」** を考えさせる。

## 3. AIとEMの役割分担

### AIが担うこと

| 役割 | 内容 |
|---|---|
| **Observe**（観測する） | Journal・議事録・Slack等の入力から情報を拾い、チーム・メンバー・プロジェクトの変化を捉える |
| **Interpret**（解釈する） | 複数の情報を関連付け、状況・傾向・懸念事項を言語化する |
| **Remember**（記憶する） | 過去の出来事・判断・状況を蓄積し、現在の状況と過去の類似ケースを関連付ける |
| **Lens Selection**（レンズを選ぶ） | 状況に応じて有効な哲学レンズを選ぶ（§4） |
| **Expand**（視点を広げる） | 現在のEMの認識から離れて、別の解釈・仮説・問題設定・見えていない情報を探索する |
| **Challenge**（前提を問い直す） | 前提・思い込み・事実と解釈の混同を検討し、「そもそもそれは本当に問題か」を問う |
| **Hypothesis**（仮説化する） | 断定できない場合は仮説のまま、判断材料として形にする |
| **Suggest**（提案する） | EMが見るべき変化・判断材料・選択肢を提示する（解決策に限らない） |
| **Grow**（学びを促す） | 組織側の観測・解釈とEM自身の振り返りを横断し、EM自身が学ぶべき視点の候補を示す |

Expand は「EMの仮説を否定するのではなく、他にもこういう見方があり得ると提示する」ためのものであり、単なる要約・言い換えや一般論の羅列で終わらせない。Challenge は否定するためではなく、**より適切な問題設定に到達するため** に行う。

Grow は Suggest とは軸が異なる。Suggest が「組織について今どう動くべきか」を示すのに対し、Grow は「EM自身が何を学ぶべきか」を示す。自己申告（チェックイン・KPT）だけに頼ると本人が既に関心を持っている点の増幅にとどまるため、組織側の観測・解釈と突き合わせ、EM自身では気づきにくい繰り返しのパターンや盲点を示す。学びの候補は開発実務に閉じ込めず、経営・事業・組織設計・マネジメント・隣接分野からの類推も含める。あくまで「こういう学びが参考になりそうです」という判断材料であり、「これを学ぶべき」という評価・断定はしない。

### EMが担うこと

| 役割 | 内容 |
|---|---|
| **Decide**（判断する） | 何が本当に重要なのか、何に対応し何に対応しないかを決める。Growが示す学びの材料から何を実際に学ぶかも決める |
| **Communicate**（伝える） | 誰に・何を・どう伝えるかを決め、メンバー・チーム・他職種と対話する |
| **Intervene**（介入する） | 実際の組織・プロジェクト・チームに働きかけ、結果を見て再び観測する |

最終的な意思決定は常にEMが行う。AIは Observe〜Grow を担い、EMは Decide〜Intervene に集中できる状態を目指す。

## 4. 哲学レンズ

AIに単なるEM業務の知識やフレームワークの知識を持たせるのではなく、**EMが状況を考えるための「哲学・思考様式」をレンズとして持たせる。** レンズは「正解を導くためのルール」ではなく、「この状況を、この考え方から見ると何が見えるか？」を考えるために使う。

| レンズ | 見る視点 |
|---|---|
| **Agile** | 顧客・利用者にとっての価値／不確実性と変化の前提／小さく届けてフィードバックを得る／継続的な学習・適応／技術的卓越性 |
| **Scrum / Empiricism** | 透明性・検査・適応。Scrumのイベントや役割をそのまま適用するのではなく、経験主義による「観測→検査→適応」の考え方をレンズとして使う |
| **Lean** | 価値／Value Stream／Flow／待ち・滞留・手戻り・ムダ／制約／継続的な改善。「価値がどのように流れているか」を見るためのレンズ |
| **DORA / Capability** | 開発指標そのものではなく、成果の背後にある組織・技術・開発システムのCapabilityを見る（結果→何が起きている？→どのCapabilityが関係？→何を阻害？→どこを変えると全体が改善する？） |
| **Design Thinking** | 本当に解くべき問題は何か／誰にとっての問題か／観測した現象と本質的な課題を分ける／仮説→小さく試す→学ぶ。「EMが問題だと思っているものが、本当に解くべき問題なのか？」を問い直す |
| **Systems Thinking** | 個別事象でなく全体を見る／要素間の関係・因果・フィードバックループ・遅延・意図しない副作用を見る／局所最適化が全体最適とは限らない |

レンズは毎回すべてを機械的に適用する必要はない。状況に応じて有効なレンズだけを、有効な数だけ使う。分析フローは次の順序で進む。

```text
Observe → Remember → Interpret → Lens Selection → Expand → Challenge → Hypothesis → Suggest
```

重要なのは、**レンズを適用して答えを出すことではなく、レンズによって「見えていなかったもの」を見つけること。**

生成AIによってコード生成・調査・文書作成・実装のコストが変化しても、価値を見る・不確実性の中で学習する・フィードバックを得る・Flowを見る・制約を見る・システム全体を見る・Capabilityを見る・問題設定を問い直す、といった思考様式は重要であり続ける。むしろ「実行」の速度が上がるほど、**何を・なぜ実行するのか、結果から何を学び、システムのどこを変えるのか** を考える重要性が高まる。そのため、Emtherは生成AIそのものを中心に置くのではなく、AI時代にも有効な普遍的な思考様式を中心に置く。

## 5. 設計原則

### 5.1 Issueを中心概念にしない

AIが観測・解釈した結果として現れる「状況」や「判断材料」の一つ（Suggestion）を最終成果物として管理し続ける設計は避ける。細かな階層化・Action Item・Priority・Why/What/Howを人間が延々と管理する仕組みは持たない。実際のタスク管理はJira・Notion等の既存ツールに委ね、Emtherは「Issueになりうる」という提案までに留める。外部ツールへの受け渡しは [`suggestion_export.md`](suggestion_export.md) を参照。

### 5.2 EMによる入力は「管理のため」ではなく「重要な情報を残すため」

すべての情報をMCP等で自動取得することを目指さない。議事録やSlackのまとめ、EM自身が「これは重要」と判断したポイント、AIには取得しにくいEMの認識・感覚・判断を人間が入力することを許容する。ただし入力した情報をさらに細かく分類・整理する作業は極力AIに寄せる。

> 「入力 → 人間が整理」ではなく、「入力 → AIが整理 → 人間は必要なら訂正」

### 5.3 AIは「答え」より「判断材料」を提供する

「これはIssueです」「PriorityはHighです」「このActionを実行してください」と決めることを目的としない。代わりに「こういう変化が起きています」「過去にも似た状況がありました」「他にもこういう見方があり得ます」「その前提はこう問い直せそうです」という形でEMの判断を支援する。

### 5.4 組織の記憶を蓄積する

単なるIssueやタスクの履歴ではなく、「何が起きていたか」「そのときどう考えていたか」「何を問題だと認識したか」「どう対応したか」「その結果どうなったか」を蓄積し、現在の状況を過去の文脈と比較できる状態を目指す。

### 5.5 情報を増やすのではなく、蒸留する

Emtherの価値は大量の情報を蓄積することそのものではない。大量の情報から「今、EMが知っておくべきこと」を取り出して提示することにある。

### 5.6 入力・出力・認知負荷を絞る

- **入力を減らす**: Journalは「イベントごとの記録」ではなく「EM自身の振り返り・思考を残す場所」。日々の出来事の逐一入力を求めない。
- **見るものを減らす**: AIが発見した情報や提案を大量に並べるのではなく、EMが注意を向けるべき重要なものとそれ以外を明確に分ける。AIの分析能力を高めることより、EMが確認・判断する情報量を抑えることを重視する。
- **思考過程は原則隠す**: AIの思考・分析過程を常に表示せず、基本は判断・結論を中心に提示し、必要な場合だけ根拠や詳細を確認できる形にする。
- **機微情報は詳細を蓄積しない**: 機微情報を含む生データをそのままEmtherや外部AIに渡さない。必要に応じてローカル環境で処理し、EMが判断するために必要な最小限の状態・変化・シグナルのみを扱う。

### 5.7 専門性は境界で安定させる

複数のAgentに役割を分けるときは、「何を専門とするか」だけでなく **「何を専門としないか（やらないこと）」を必ず書く。** 肯定文の役割説明だけでは同じ事実に対して各Agentが似た答えを返してしまい、専門チームとしての差分が生まれない。役割定義（何者か）・観点（どのレンズ・チェックリストで見るか）・コンテキスト（何を渡すか）の3層で差分化し、共通の出力規約（提案／Yield）は維持したまま、中身の視点と材料だけを変える。

## 6. 主要概念

### MVV / Goal / Policy

組織方針・目標の扱いの正本は `docs/goal_policy_model.md`（設計思想）と `docs/goal_policy_model_plan.md`（実装計画）。要点のみここに記す。

- **MVV**（Mission/Vision/Values）: 組織として長期的に大切にする価値観・方向性。比較的安定した情報で、日々の判断の背景として常時注入する。
- **Goal**: EMとして見据えている「到達したい状態」。SMARTである必要はなく、曖昧な段階から登録してよい。OKR（Objective/Key Result）は、Goalを具体化したい場合に任意で使う手段の一つであり、必須の構造ではない（GoalとObjectiveは別エンティティで、Objective側から任意にGoalへリンクする）。
- **Policy**: Goalに向かう際にEMが守りたい判断原則（大切にすること・優先すること・やらないこと・判断に迷ったときの原則、など）。固定欄ではなく自由記述の複数エントリとして持つ（方針4「入力項目を埋めることを目的にしない」に合わせるため）。

MVV → Goal/Policy/Theme → 日々の観測・判断、という緩やかな構造が基本であり、OKRなどの具体的な管理手法は必要に応じてその中に持ち込める設計にする。

### Journal

事実の感知の起点。EMが1日を振り返りながら必要なことを記録する場所であり、イベントごとの逐一記録は求めない。AIによる問いかけを通じて振り返りを支援する。チャットログ等の外部テキストは Observation Dump として取り込み、AIが意味のある事実のかたまりに分割したうえで、採用分だけ通常のJournalにする（分割はIssue化を意味しない）。

### Suggestion（旧称: Issue）

AIの観測・解釈の結果として現れる「状況」や「判断材料」であり、EMが細かく進捗管理する対象ではない。`reviewStatus`（未確認・確認中・様子見・完了）で最小限の状態だけを持ち、EMが依頼したときに限りAIが既存Suggestionのポートフォリオを整理できる（意図的に残しているものが裏で自動的に書き換わることはない）。

### Yield

AIからEMへの介入要求。3種類の性質を持つ。

- **decide**: EMの判断が必要
- **inform**: 情報共有のみ
- **commit**: EMのコミットメントが必要

Yieldは「AIがすべてを提案として出し尽くす」のではなく、EMが本当に注意を向けるべきタイミングだけを明示するための仕組みである。

### Agentチーム構成

Lead Agent が論点を分解し、専門Agent（People / Process / Tech / Product）への振り分け・統合判断・EMへのYieldを担う。各専門Agentは自分の専門領域だけでなく「やらないこと」を持ち、専門外の論点はLeadに戻す（§5.7）。哲学レンズ（§4）は全Agent共通の基盤であり、Agentごとに「効きやすいレンズ」の傾向はあっても、使用を強制・制限しない。

### Grow / チェックイン・KPT

EM自身の学びを促す軸。日次・週次の振り返り（チェックイン・KPT）を、組織側のObserve/Interpret/Rememberの蓄積と突き合わせ、EM自身では気づきにくいパターンや盲点を提示する（§3）。

### Theme / 蒸留（Knowledge Distillation）

Journal自動分析や壁打ちを個別の類似度検索だけに任せず、明示的な蒸留成果物（テーマ解釈）を持ち、EMが採用したものだけを以降の壁打ちの前提として注入する。情報を増やすのではなく蒸留するという原則（§5.5）の実装面での現れ。テーマの生成経路は観測からの後追い（週次蒸留）だけでなく、Goalから先に候補を置く経路も持つ（`docs/goal_policy_model_plan.md` Decision 3）。

### プライバシー・機微情報の扱い

実名等はPERSON_nのような形でマスクし、実名対応表はリポジトリ外の保護された領域に分離して保持する。機微情報を含む生データの詳細を蓄積せず、判断に必要な最小限のシグナルだけを扱う（§5.6）。Emtherはローカル環境で動作する単一ユーザー向けツールであり、この前提が機微情報の扱い方の土台になっている。

## 7. 想定フロー

- **日中**: EMがJournalやObservation Dumpで事実を残す。AIはObserve〜Rememberを継続し、必要なときだけYieldでEMの判断を求める。
- **朝**: 「今日、チームについて何を知っておくべきだろう？」に対し、昨日から変わったこと・気になる兆候・良い状態・過去との比較・判断する価値がありそうなことを提示する。
- **夕方**: EMが1日を振り返る（チェックイン）。
- **週次**: チェックイン・KPTと組織側の観測・解釈を突き合わせ、Growとして学びの候補を提示する。テーマの蒸留・週次レポートもこのリズムに乗る。
- **月次**: より長い時間軸での比較・レポートを行う。

EMは Observe → Interpret → Remember → Lens Selection → Expand → Challenge → Hypothesis → Suggest → Grow をAIに任せ、Decide → Communicate → Intervene に集中できる状態を目指す。

## 8. 成功条件

Emtherを使うことで、

> 「Suggestionを管理する時間」が減るのではなく、
> 「状況を理解するために情報を行ったり来たりする時間」が減る。

そして最終的に、

> EMが、自分一人では覚えておけない量の組織コンテキストを持った状態で、より良い判断ができる。

ことを成功とする。

## 9. 変遷（1st〜4th pivotの要約）

Emtherはこの思想に一度で到達したわけではなく、複数回の見直し（ピボット）を経ている。詳細な検討過程・当時の課題認識・移行計画は `docs/archive/` に残しており、要約のみここに記す。

1. **1st（初期構想）**: Issue Workspaceやツリー構造のOrg Contextなど、Issue中心・階層管理型のUXを構想（`docs/archive/first_implession/`）。
2. **2nd（アーキテクチャ／利用方針）**: Vite + Honoへのアーキテクチャ移行（`docs/archive/2nd_architecture/`）と並行し、「Issueを中心概念にしない」「入力は管理のためでなく残すため」等の基本方針を策定（`docs/archive/2nd_pivot_version/pivot_policy.md` → 本書§5に統合）。
3. **3rd（分析フローの拡張）**: Expand / Challengeを分析フローに追加（後継の4th pivot配下に実体）。
4. **4th（利用方針の見直し）**: 「EMは考え判断する人、AIは思い出させ整理し注意を向ける人」という基本コンセプトを明文化し、AIアウトプットの絞り込み・思考過程の秘匿・機微情報の非蓄積を方針化（`docs/archive/4th_pivot/`）。
5. **哲学レンズの導入（2026-09-20）**: Agile/Scrum・Empiricism/Lean/DORA・Capability/Design Thinking/Systems Thinkingの6レンズと、Lens Selection/Hypothesisを分析フローに追加（`docs/archive/ai_philosophy.md`、実装記録は`docs/archive/ai_philosophy_implementation_plan.md`）。

これらの変遷を経て、Issue管理・進捗トラッキングのUIは大部分が撤去され、AIが提示する判断材料（Suggestion）とEMの判断（Yield/Decide）を軸にした現在の形に至っている。
