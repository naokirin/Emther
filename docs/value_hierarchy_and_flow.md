## 0. 課題の本質

このプロダクトは、広範囲の業務に広い視点と判断を求められ忙殺されやすい EM をサポートするために作っている。

現状は、情報入力・課題の棚卸し・情報更新・AI アウトプットの確認など、**多岐にわたる作業を EM が逐一担う設計**に寄りがちで、もともと作りたかった価値（関心を現場の効率化から組織設計とミッション実現へ引き上げる）を作りきれていない。

個々の機能（Journal、相談、Issue、OKR、優先テーマ、蒸留、Vitals、Reports、People など）は揃ってきている。  
**最終的な課題は次に収束する:**

1. **適切な各構造の接続**（OKR ↔ テーマ ↔ Issue ↔ Journal／人／チーム）
2. **ユーザーストーリーに沿ったフローに UI/UX が一致していること**（日・週・月／半期）
3. **メンバー・チーム評価を、OKR／Values と Journal 由来の日常ログで接続すること**（§5。テーマ／Issue は EM 介入線であり貢献の主経路にしない）

部品追加より、「接続」と「物語への編入」が先、という認識（`em_human_story_and_ux.md`）と一致する。

## 1. 提供価値の明確化（3軸）

今後の設計・優先判断は、次の3軸で「何を解いているか」を明示してから行う。

| 軸 | 問い | このメモでの答えの方向 |
|---|---|---|
| **業務フロー** | EM の仕事の順序・リズムは何か（適正化を含む） | 目標起点でテーマを置き、観測で修正。日次は記録を軽く・判断を圧縮。期には評価・フィードバック |
| **体験（ユーザーストーリー）** | 朝・日中・夜／週／半期に何が「成功」か | 「今日向き合う組織の問いを選び、介入し、変化を読む」。期には「成果と Value の両面で人とチームを語れる」 |
| **ソリューション** | プロダクトが代わりに担う／圧縮するものは何か | 階層接続の可視化、AI による整理・優先・バイタル、蒸留による深い相談、**評価ドラフト（根拠付き）**、時間軸 UI |

この3軸が揃わない機能追加は、画面と作業を増やし、忙殺を悪化させやすい。

## 2. あるべき階層構造

```text
憲法・戦略（MVV / 制約 / 体制）     ←── 評価レンズB: Value（言動・模範）
  └─ OKR（Objective → Key Result） ←── 評価レンズA: 目標・成果への貢献
       └─ テーマ（今期〜今月の焦点・解釈）     ※ EM 介入の焦点（メンバー貢献の主経路ではない）
            └─ Issue（介入単位）               ※ 同上
                 └─ Action Item / 子 Issue

Journal（事実）──AI仮置き──→ メンバーの「日常の評価」ログ（A/B 分離）
テーマ / Issue ────────（弱い任意信号）──┘
```

### 2.1 各層の役割

| 層 | 役割 | 現状の主な置き場 |
|---|---|---|
| MVV（とくに Values） | 会社として望ましい言動の規範。評価レンズ B の正本 | `/org` Strategy |
| OKR | 最終目標と計測可能な結果。判断の主軸／評価レンズ A の正本 | `/org` Objectives |
| テーマ | 「今、組織として何を解くか」の焦点。**EM が積極関与すべきか**の媒介 | `OrgTheme`、Dashboard「現在の優先テーマ」 |
| Issue | 介入（Why/What/How）。**EM の追跡・介入単位** | `/issues`、`focus` / `normal` / `parked` |
| Journal | 現場の事実・感知。**メンバー貢献評価の主材料** | Quick Journal / `/journal` |
| People / Team | 人・チーム軸の束ねと、日常の評価ログ／期次読み出し面 | `/people`、`/teams`、Vitals |

### 2.2 現状の接続ギャップ

- **Objective とテーマが近いのに関係が見えない**  
  「最終目標とどうつながっているか（または、いないのか）」が UI 上で弱い。
- **Issue → テーマ / Objective の効き方が弱い**  
  `keyResultId` はあるが、テーマ紐付けや「この介入はどの焦点に効くか」が朝の物語に乗っていない（戦略線は部品済み・編入不足）。
- **結果として**  
  フラットに並ぶ粒度の違う Issue を上から消化する、「とりあえず眼の前の課題をやる」アンチパターンを促進しうる。

### 2.3 テーマ生成の順序（重要）

現状の蒸留は、Journal / Issue 等の観測から週次（または手動）でテーマ候補を出し、採用する流れ（`knowledge_distillation.md`）。これは **遅行評価・修正** としては有用だが、**主題の起点としては順序が逆**になりやすい。

| あるべき | 現状に寄りがちな動き |
|---|---|
| OKR 等の大きな目標から、やるべきテーマが先に出る | 観測の束ねからテーマが後から生まれる |
| 観測された実態で、直近の優先テーマが**修正**される | 修正機構としての蒸留が、主題そのものに見える |

方針案:

1. **期初・OKR 更新時**: Objective/KR から「候補テーマ」を先に置く（人間確定または AI 提案→採用）
2. **週次蒸留**: 観測との差分でテーマの追加・統合・降格・文言修正（遅行フィードバック）
3. **日次**: テーマを前提に Issue / 「今日の問い」を圧縮（テーマを毎日ゼロから作らない）

## 3. 時間軸フローとプロダクト利用の接続

### 3.1 日次ループ（感知を軽く、判断を圧縮）

提案するリズム:

1. **就業前〜朝**: 前日夜に書いたまとまった Journal から、レポートと共に振り返り → Journal / Issue の棚卸し → **今日やることの決定**
2. **日中**: 業務・介入（逐一の構造化入力を主作業にしない）
3. **夕〜就業前**: 今日あったことを **分割を考えず 10〜15 分で書き連ねる**

Journal まわりの方針:

- **記録と構造化を分離**: raw は必ず保存。分割・統合・Issue 候補は AI 提案（翌朝バッチ可）
- 「Journal の事実単位への分割／統合」と「介入候補（Issue）への昇格」は二段に分ける
- あわせて、人物が含まれる事実から **日常の評価ログ（§5）** を AI が仮置きする（目標貢献 / Value 体現。EM の日次確認を必須にしない）
- HITL は全文1件ずつの確認ではなく、**例外レビュー**（信頼度が低い境界だけ）に寄せる
- 現状の Quick Journal 逐次投稿・都度校正・都度分析を、主経路から外していく方向

棚卸しだけでは Issue 忙殺は残る → **§4 の優先度圧縮**と **§2 の階層**がセット。

### 3.2 週次

- テーマの見直し（蒸留＝修正・再優先）
- 週次レポート（観測スナップショット＋所感）
- 優先帯（focus 集合）の入れ替え
- （任意）日常の評価ログの差分・観測不足の人／チーム — 本評定の確定は期に寄せる

### 3.3 月／半期

- OKR 評価・Objective/KR の更新
- テーマの再設定（目標起点に戻す）
- 月次レポート、介入効果・Vitals の振り返り
- **メンバー・チーム評価**（§5）: 日常の評価ログを A/B に束ねて読み、1on1／キャリブレーション材料にする

### 3.4 UI への落とし込み（方向）

| 時間 | ユーザーが最初に見るべきもの | 載せすぎないもの |
|---|---|---|
| 朝（今日タブ） | 今期の焦点（テーマ）に対する「今日の問い」N 件、判断待ちの例外 | 全 Run・全 Issue・全校正キュー、評価フォーム、日常評価ログの全件確認 |
| 週 | テーマ修正候補、週次レポート、観測不足の人／チーム | 日次オペレーション一覧の再掲だけ |
| 期 | OKR 進捗、未接続 Issue／効いていないテーマ、**人・チーム評価の束ね（A/B・根拠は Journal ログ中心）** | 細かい Action Item、日次の生 Run 一覧 |

成功条件（既存ストーリーと同一）: 朝に「今日 EM として向き合う組織課題」が **3〜5 件**に絞られる。  
期の成功条件（追加）: 感覚だけで評定せず、**目標への寄与**と **Value に照らした言動**を、日常ログの根拠付きで語れる。

## 4. Issue 優先度・トリアージ（認知負荷を下げる）

### 4.1 現状

- Issue 優先度はポートフォリオ帯のみ: `focus` / `normal` / `parked`（＋ `focusOrder`）
- RICE / 工数×効果などの数値スコアは未導入
- 粒度の違う Issue がフラットに並ぶと、帯付け自体が「全部読んでから決める」作業になる

### 4.2 指標候補（一般的なもの → EM 向け読み替え）

| 指標 | 概要 | EM 文脈 |
|---|---|---|
| Value / Effort | 2×2 | 組織レバレッジ vs 介入コスト |
| ICE | Impact × Confidence × Ease | 軽い並べ替え向き |
| RICE | Reach × Impact × Confidence / Effort | Reach＝影響人数・チーム数。やや重い |
| WSJF / CD3 | Cost of Delay ÷ Duration | **放置リスク ÷ 片付ける期間**。期限付き組織リスクに強い |
| Severity × Likelihood | リスク行列 | 離職・バーンアウト・障害再発など |
| Blast radius | 影響半径 | 粒度混在の層分け |
| Reversibility / Leverage | 可逆性・仕組み介入か | 個人対応と組織設計を同列にしない |

MoSCoW はスコープ向きで日次トリアージには粗い。Eisenhower は緊急に引きずられやすいので、緊急＝Intake、重要＝focus 帯、のように役割分離する。

### 4.3 使い方（認知負荷を上げない）

EM に毎回マトリクスを埋めさせない。

```text
AI 推定スコア（複数軸）
  → 推奨帯 focus | normal | parked（＋今日の上位 N 件）
  → EM は「この並びでよいか／例外はどれか」だけ見る
```

実務向け最小セット案:

| 軸 | 役割 |
|---|---|
| 放置リスク（CoD / costOfDelay） | 「今見なくてよいか」の主軸 |
| 介入コスト（Effort） | 短時間か重い介入か |
| 影響半径 | 粒度違いの混在を防ぐ |
| 確信度 | 材料不足は今日の判断から外し Yield／要情報へ |

並べ替えのイメージ:

\[
\text{優先スコア} \approx \frac{\text{放置リスク} \times \text{影響半径}}{\text{介入コスト}} \times \text{確信度}
\]

既存の `focus` / `normal` / `parked` は残し、**スコアは帯付けの内部根拠**、UI の主面は圧縮キューと例外レビューとする。

粒度対策の併用:

- 一覧の主面は親 Issue（Action Item / 子は作業面）
- テーマ単位へのロールアップ
- 更新も Journal も無い Issue の parked 候補化

## 5. メンバー・チーム評価（直交だが必須の EM 業務）

課題の棚卸し・介入ポートフォリオ（§2〜4）とは **少し直交**する。ただし EM がやらなければならない業務であり、プロダクトの提供価値に含める。

### 5.1 二つの評価観点（混ぜない）

| 観点 | 問い | 主な参照正本 | 見たいもの |
|---|---|---|---|
| **A. 成果・目標貢献** | 組織・チームの目標に近づけたか。事業・組織の成果に貢献したか | OKR（Objective/KR）、チーム目標 | Journal に残る事実が、どの目標にどう寄与したかの解釈 |
| **B. Value 適合** | MVV（とくに **Values**）に照らして適切な言動を取れていたか。会社として模範になっていたか | Strategy の Values（必要なら Mission/Vision も文脈） | Journal に残る言動が、どの Value をどう体現／乖離したかの解釈 |

**単一スコアに潰さない。** 「成果は出ているが Value と乖離」「Value は体現しているが成果への接続が弱い」を見えるようにするのが目的である。

### 5.2 テーマ / Issue との関係を弱める（重要）

このプロダクトにおける **テーマ / Issue は、「EM が積極的に関与すべきか」が優先**されている。  
そのため、メンバーが日々積極的にやるべきこと・貢献の実態と **ズレうる**。

方針:

- メンバー貢献の主経路を **テーマ / Issue 紐付けにしない**（ゼロ必須ではないが、弱める）
- テーマ / Issue 上の言及は、あっても **弱い任意信号**（補助）。評価 A/B の主根拠にしない
- 評価の正本リンク先は **OKR（およびチーム目標）と Values** とする

そうしないと、「EM の介入バックログに載っていること」＝「メンバーの貢献」という誤読が起きる。

### 5.3 主経路: Journal → 日常の評価ログ（AI 仮置き）

日々の主作業を「評価シート記入」にしない。代わりに、Journal の事実からメンバー情報へ **仮置きログ**を積む。

```text
Journal（誰が・何をした／どう振る舞ったかの事実）
  → AI が仮置きログを People 側へ付与
     例: 「この言動は Objective/KR ○○ に、△△という意味で貢献している」
     例: 「この言動は Value □□ を、◇◇という意味で体現している」
     （乖離・懸念も同様に仮置き可。断定せず根拠 Journal を残す）
  → ログは未確定（provisional）。EM の日次承認は不要
  → 週〜期に束ねて読み、例外だけ訂正／捨てる／確定に使う
```

方針:

- **根拠必須**: 各ログは元 Journal（および要約根拠）を参照する
- **A/B をフィールドで分ける**: 目標貢献ログと Value 体現ログを混在させない
- **仮置きであることの明示**: 自動確定・人事評定の代替にしない
- **Values は武器化しない**: 監視チェックリスト化や自動減点を主目的にしない
- **チーム評価**: 個人ログの単純合算ではなく、チーム目標・チームとして見える協働を別枠で読む
- **読み出し面**: People 詳細／期次の束ね。朝の「次の1手」に評価フォームやログ全件確認を載せない（§3.4）

### 5.4 現状とのギャップ

| あるもの | 評価として足りない点 |
|---|---|
| People ハブ（プロファイル・Journal・関連 Issue） | 日常の評価ログ（A/B・仮置き）がない。関連 Issue 表示は貢献の主経路にしない |
| Team Vitals / sentiment | 健全性・観測量の信号であり、**成果貢献でも Value 適合でもない** |
| `/growth` | **EM 本人**の自己チェックイン／KPT。メンバー評価ではない |
| MVV・Objectives の Agent 注入 | 壁打ち前提にはなるが、Journal→人物ログの出力形式としては未接続 |
| テーマ / Issue | EM 介入管理。メンバー貢献の主材料にすると目的がズレる |

### 5.5 階層・フローとの接続

- **A** の正本は OKR／チーム目標。テーマ→Issue の接続強化（§2）は **EM の介入品質**のためであり、メンバー貢献評価の前提条件にはしない
- **B** は MVV（Values）が空だと成立しない。初回セットアップの MVV は評価の前提でもある
- Journal 一括記録（§3.1）が厚いほど、日常の評価ログの材料が増える（記録と評定入力を分離）
- 期次の「評価ドラフト」は、日常ログの束ね＋不足の明示であり、ゼロからシートを埋める作業にしない

## 6. ソリューション整備の柱

今後の実装・改善は、次の柱に紐づけて優先する。

### 6.1 階層の接続（構造）

- OKR → テーマ → Issue の明示リンク（テーマ↔Objective/KR、Issue↔テーマ）— **EM 介入線**
- 「つながっていない」も可視化（戦略に載らない介入の明示）
- 朝の物語に「今期のために何を解いているか」を載せる
- メンバー評価線は Journal → OKR / Values を主とし、テーマ / Issue は弱い任意信号に留める

### 6.2 AI 自動化（作業の圧縮）

- Journal 一括入力 → 分割／統合 → Issue 作成・修正提案
- テーマ見直し・優先度（帯）提案
- メンバー／チームの Vitals 監視と、今日 N 件への昇格判断材料化
- **Journal → 日常の評価ログ（A/B・仮置き・根拠付き）**。期次はその束ね。確定・大きな訂正は EM
- 原則 AI 主導、EM は例外上書き（`em_ui_ux_issue.md` と同方向）

### 6.3 蒸留と深い相談役（学習）

- 蓄積（Journal / Issue / テーマ / OKR / 人 / Values／日常の評価ログ）を前提にした相談
- 蒸留は「知識・解釈の版管理」＋週次のテーマ修正に使う
- より適切な Issue / テーマ設定、および評価ログ品質向上のためのコンテキスト注入（採用済みのみ、という現行方針は維持しうる）

### 6.4 時間軸 UI（体験の一致）

- 日: 今日タブ、朝サマリー、夜の書き連ね入口（評価ログは裏で仮置き）
- 週: 蒸留（修正）、週次レポート、テーマ入れ替え、観測不足の提示
- 月／半期: OKR 評価、テーマ再設定、月次レポート、**日常評価ログを束ねたメンバー・チーム評価（A/B）**

## 8. 今後の対応候補（優先の問い）

実装に落とす前に、判断が必要な問い:

1. テーマの正本は「OKR 由来」か「採用済み OrgTheme」か。両者の ID リンクモデルは何か
2. Issue 必須紐付けは KR かテーマか、両方か、どちらか一方＋警告か（EM 介入線の話）
3. 夜の Journal ダンプの主入口を Dashboard に置くか、専用モードにするか
4. スコア軸の採用セット（§4.3 の4軸で足りるか）
5. 朝 UI の主問を「今日の組織の問い」1文＋判断3件に固定する手順（既存 P0 と統合）
6. 日常の評価ログの永続モデル（People 配下か、KnowledgeEvent の interpretation か）と、仮置き→確定の状態機械
7. Values / Objective・KR への参照は ID 必須か、生成時点の文言スナップショット併持か
8. テーマ / Issue 由来の弱い信号をログに載せるか、完全に出さないか
9. チーム評価と個人評価のロールアップ規則（単純合算を避ける）をどうするか
10. 乖離・懸念ログの扱い（表彰的ログと対称にするか、EM のみ表示か）

## 9. 一言まとめ

**機能は揃った。足りないのは、OKR→テーマ→Issue の階層と日／週／期のフローに UI が一致していること、AI が判断を N 件に圧縮すること、および Journal から目標貢献と Value 体現を仮置きログとして人に積めることである。テーマ／Issue は EM 介入の道具であり、メンバー貢献の主経路にしない。**
