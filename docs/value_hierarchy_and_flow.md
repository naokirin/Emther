## 0. 課題の本質

このプロダクトは、広範囲の業務に広い視点と判断を求められ忙殺されやすい EM をサポートするために作っている。

現状は、情報入力・課題の棚卸し・情報更新・AI アウトプットの確認など、**多岐にわたる作業を EM が逐一担う設計**に寄りがちで、もともと作りたかった価値（関心を現場の効率化から組織設計とミッション実現へ引き上げる）を作りきれていない。

個々の機能（Journal、相談、Issue、OKR、優先テーマ、蒸留、Vitals、Reports など）は揃ってきている。  
**最終的な課題は次の2点に収束する:**

1. **適切な各構造の接続**（OKR ↔ テーマ ↔ Issue ↔ Journal／人／チーム）
2. **ユーザーストーリーに沿ったフローに UI/UX が一致していること**（日・週・月／半期）

部品追加より、「接続」と「物語への編入」が先、という認識（`em_human_story_and_ux.md`）と一致する。

## 1. 提供価値の明確化（3軸）

今後の設計・優先判断は、次の3軸で「何を解いているか」を明示してから行う。

| 軸 | 問い | このメモでの答えの方向 |
|---|---|---|
| **業務フロー** | EM の仕事の順序・リズムは何か（適正化を含む） | 目標起点でテーマを置き、観測で修正。日次は記録を軽く・判断を圧縮 |
| **体験（ユーザーストーリー）** | 朝・日中・夜／週／半期に何が「成功」か | 「今日向き合う組織の問いを選び、介入し、変化を読む」 |
| **ソリューション** | プロダクトが代わりに担う／圧縮するものは何か | 階層接続の可視化、AI による整理・優先・バイタル、蒸留による深い相談、時間軸 UI |

この3軸が揃わない機能追加は、画面と作業を増やし、忙殺を悪化させやすい。

## 2. あるべき階層構造

```text
憲法・戦略（MVV / 制約 / 体制）
  └─ OKR（Objective → Key Result）
       └─ テーマ（今期〜今月の焦点・解釈）
            └─ Issue（介入単位）
                 └─ Action Item / 子 Issue（実行・分解）
```

### 2.1 各層の役割

| 層 | 役割 | 現状の主な置き場 |
|---|---|---|
| OKR | 最終目標と計測可能な結果。判断の主軸 | `/org` Objectives、Issue の `keyResultId` |
| テーマ | 「今、組織として何を解くか」の焦点。OKR を日々意識しにくさを媒介する | `OrgTheme`、Dashboard「現在の優先テーマ」 |
| Issue | 介入（Why/What/How）。追跡する単位 | `/issues`、`focus` / `normal` / `parked` |
| Journal | 現場の事実・感知 | Quick Journal / `/journal` |

### 2.2 現状の接続ギャップ

- **Objective とテーマが近いのに関係が見えない**  
  「最終目標とどうつながっているか（または、いないのか）」が UI 上で弱い。
- **Issue → テーマ / Objective の効き方が弱い**  
  `keyResultId` はあるが、テーマ紐付けや「この介入はどの焦点に効くか」が朝の物語に乗っていない（戦略線は部品済み・編入不足）。
- **結果として**  
  フラットに並ぶ粒度の違う Issue を上から消化する、「とりあえず眼の前の課題をやる」アンチパターンを促進しうる。

### 2.3 テーマ生成の順序（重要）

現状の蒸留は、Journal / Issue 等の観測から週次（または手動）でテーマ候補を出し、採用する流れ（`knowledge_distillation.md`）。これは **遅行評価・修正** としては有用だが、**主題の起点としては順序が逆**になりやすい。

| あるべき | 現状に寄りがちな動き |
|---|---|
| OKR 等の大きな目標から、やるべきテーマが先に出る | 観測の束ねからテーマが後から生まれる |
| 観測された実態で、直近の優先テーマが**修正**される | 修正機構としての蒸留が、主題そのものに見える |

方針案:

1. **期初・OKR 更新時**: Objective/KR から「候補テーマ」を先に置く（人間確定または AI 提案→採用）
2. **週次蒸留**: 観測との差分でテーマの追加・統合・降格・文言修正（遅行フィードバック）
3. **日次**: テーマを前提に Issue / 「今日の問い」を圧縮（テーマを毎日ゼロから作らない）

## 3. 時間軸フローとプロダクト利用の接続

### 3.1 日次ループ（感知を軽く、判断を圧縮）

提案するリズム:

1. **就業前〜朝**: 前日夜に書いたまとまった Journal から、レポートと共に振り返り → Journal / Issue の棚卸し → **今日やることの決定**
2. **日中**: 業務・介入（逐一の構造化入力を主作業にしない）
3. **夕〜就業前**: 今日あったことを **分割を考えず 10〜15 分で書き連ねる**

Journal まわりの方針:

- **記録と構造化を分離**: raw は必ず保存。分割・統合・Issue 候補は AI 提案（翌朝バッチ可）
- 「Journal の事実単位への分割／統合」と「介入候補（Issue）への昇格」は二段に分ける
- HITL は全文1件ずつの確認ではなく、**例外レビュー**（信頼度が低い境界だけ）に寄せる
- 現状の Quick Journal 逐次投稿・都度校正・都度分析を、主経路から外していく方向

棚卸しだけでは Issue 忙殺は残る → **§4 の優先度圧縮**と **§2 の階層**がセット。

### 3.2 週次

- テーマの見直し（蒸留＝修正・再優先）
- 週次レポート（観測スナップショット＋所感）
- 優先帯（focus 集合）の入れ替え

### 3.3 月／半期

- OKR 評価・Objective/KR の更新
- テーマの再設定（目標起点に戻す）
- 月次レポート、介入効果・Vitals の振り返り

### 3.4 UI への落とし込み（方向）

| 時間 | ユーザーが最初に見るべきもの | 載せすぎないもの |
|---|---|---|
| 朝（今日タブ） | 今期の焦点（テーマ）に対する「今日の問い」N 件、判断待ちの例外 | 全 Run・全 Issue・全校正キュー |
| 週 | テーマ修正候補、週次レポート | 日次オペレーション一覧の再掲だけ |
| 期 | OKR 進捗と未接続 Issue／効いていないテーマ | 細かい Action Item |

成功条件（既存ストーリーと同一）: 朝に「今日 EM として向き合う組織課題」が **3〜5 件**に絞られる。

## 4. Issue 優先度・トリアージ（認知負荷を下げる）

### 4.1 現状

- Issue 優先度はポートフォリオ帯のみ: `focus` / `normal` / `parked`（＋ `focusOrder`）
- RICE / 工数×効果などの数値スコアは未導入
- 粒度の違う Issue がフラットに並ぶと、帯付け自体が「全部読んでから決める」作業になる

### 4.2 指標候補（一般的なもの → EM 向け読み替え）

| 指標 | 概要 | EM 文脈 |
|---|---|---|
| Value / Effort | 2×2 | 組織レバレッジ vs 介入コスト |
| ICE | Impact × Confidence × Ease | 軽い並べ替え向き |
| RICE | Reach × Impact × Confidence / Effort | Reach＝影響人数・チーム数。やや重い |
| WSJF / CD3 | Cost of Delay ÷ Duration | **放置コスト ÷ 片付ける期間**。期限付き組織リスクに強い |
| Severity × Likelihood | リスク行列 | 離職・バーンアウト・障害再発など |
| Blast radius | 影響半径 | 粒度混在の層分け |
| Reversibility / Leverage | 可逆性・仕組み介入か | 個人対応と組織設計を同列にしない |

MoSCoW はスコープ向きで日次トリアージには粗い。Eisenhower は緊急に引きずられやすいので、緊急＝Intake、重要＝focus 帯、のように役割分離する。

### 4.3 使い方（認知負荷を上げない）

EM に毎回マトリクスを埋めさせない。

```text
AI 推定スコア（複数軸）
  → 推奨帯 focus | normal | parked（＋今日の上位 N 件）
  → EM は「この並びでよいか／例外はどれか」だけ見る
```

実務向け最小セット案:

| 軸 | 役割 |
|---|---|
| 放置コスト（CoD） | 「今見なくてよいか」の主軸 |
| 介入コスト（Effort） | 短時間か重い介入か |
| 影響半径 | 粒度違いの混在を防ぐ |
| 確信度 | 材料不足は今日の判断から外し Yield／要情報へ |

並べ替えのイメージ:

\[
\text{優先スコア} \approx \frac{\text{放置コスト} \times \text{影響半径}}{\text{介入コスト}} \times \text{確信度}
\]

既存の `focus` / `normal` / `parked` は残し、**スコアは帯付けの内部根拠**、UI の主面は圧縮キューと例外レビューとする。

粒度対策の併用:

- 一覧の主面は親 Issue（Action Item / 子は作業面）
- テーマ単位へのロールアップ
- 更新も Journal も無い Issue の parked 候補化

## 5. ソリューション整備の柱

今後の実装・改善は、次の柱に紐づけて優先する。

### 5.1 階層の接続（構造）

- OKR → テーマ → Issue の明示リンク（テーマ↔Objective/KR、Issue↔テーマ）
- 「つながっていない」も可視化（戦略に載らない介入の明示）
- 朝の物語に「今期のために何を解いているか」を載せる

### 5.2 AI 自動化（作業の圧縮）

- Journal 一括入力 → 分割／統合 → Issue 作成・修正提案
- テーマ見直し・優先度（帯）提案
- メンバー／チームの Vitals 監視と、今日 N 件への昇格判断材料化
- 原則 AI 主導、EM は例外上書き（`em_ui_ux_issue.md` と同方向）

### 5.3 蒸留と深い相談役（学習）

- 蓄積（Journal / Issue / テーマ / OKR / 人）を前提にした相談
- 蒸留は「知識・解釈の版管理」＋週次のテーマ修正に使う
- より適切な Issue / テーマ設定のためのコンテキスト注入（採用済みのみ、という現行方針は維持しうる）

### 5.4 時間軸 UI（体験の一致）

- 日: 今日タブ、朝サマリー、夜の書き連ね入口
- 週: 蒸留（修正）、週次レポート、テーマ入れ替え
- 月／半期: OKR 評価、テーマ再設定、月次レポート

## 7. 今後の対応候補（優先の問い）

実装に落とす前に、判断が必要な問い:

1. テーマの正本は「OKR 由来」か「採用済み OrgTheme」か。両者の ID リンクモデルは何か
2. Issue 必須紐付けは KR かテーマか、両方か、どちらか一方＋警告か
3. 夜の Journal ダンプの主入口を Dashboard に置くか、専用モードにするか
4. スコア軸の採用セット（§4.3 の4軸で足りるか）
5. 朝 UI の主問を「今日の組織の問い」1文＋判断3件に固定する手順（既存 P0 と統合）

## 8. 一言まとめ

**機能は揃った。足りないのは、OKR→テーマ→Issue の階層と、日／週／期のフローに UI が一致していること、および AI が「仕事を増やす」のではなく「判断を N 件に圧縮する」ことである。**
