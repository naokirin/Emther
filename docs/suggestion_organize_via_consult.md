# 既存提案の整理（相談経由）方針

作成日: 2026-09-16  
性質: **今後実装するときの方針正本**（未実装）

---

## 0. 課題

相談エージェントが既存提案に対してできる書き込みは、実質次に限られている。

- **新規**提案として残す（起票）
- 他提案への**メモ追記案**（採用まで本体不変）
- 読むこと（注入の類似上位＋ `lookup`）

そのため、提案が数十件に増えたとき、

> 「提案を整理して」と AI に頼み、確認状態・確認優先度などの細かい調整まで任せたい

という用途に使えない。EM が全件を手で見る必要が出て、ピボット後の「提案」も再び管理負担になりうる。

---

## 1. 目的

EM が `/chat` で明示的に依頼したときだけ、AI が**既存提案のポートフォリオを整理**し、EM が一括で反映できるようにする。

成功条件:

- 件数が増えても、朝や日常で「全部を人が見る」必要がない
- 意図的に `focus` 等にしておいた提案が、**依頼していないのに裏で書き換わらない**
- 整理の根拠が相談 Run に残り、後から追える

---

## 2. 決定事項（2026-09-16）

| # | 問い | 決定 |
|---|---|---|
| 1 | `done`（確認済み／もう追わない）を AI が付けてよいか | **よい** |
| 2 | 変更してよいフィールドの範囲 | **基本すべて可**（種類で Yield 必須に分けない） |
| 3 | 入口 | **相談で「提案を整理して」等と頼むときのみ** |
| — | 裏での自動書き換え（バッチ・朝サマリー・停滞監視からの本体更新） | **しない** |

「基本すべて可」は、**変更種類の制限を設けない**という意味である。  
「裏で自動」は禁止するため、反映は相談結果に対する **EM の明示操作（まとめて反映）** とする。

---

## 3. 入口と禁止事項

### 3.1 入口（唯一）

- `/chat`（何でも相談）で EM が整理を依頼する（EM Trigger）
- 依頼例: 「提案を整理して」「未確認の提案を圧縮して」「重複をまとめて」

### 3.2 やらないこと

- Journal 自動分析・朝サマリー・週次蒸留・提案更新分析（`auto-issue-update`）などから、**既存提案の `reviewStatus` / `confirmPriority` 等をサイレント更新しない**
- 依頼していない Run の完了時に、既存提案へ状態変更を書き込まない
- 「トリアージは AI 主導」の将来メモ（`em_ui_ux_issue.md`）を、本機能では **バックグラウンド自律書き換え** としては解釈しない

理由: EM が意図的に `focus` 等にした提案が、気づかないうちに降格・完了されることを防ぐため。

---

## 4. AI が扱ってよい変更

対象は既存 `Suggestion`（実在 ID）。新規起票やメモ追記の既存経路は維持してよい。

変更してよい例（制限しない）:

| フィールド／操作 | 例 |
|---|---|
| `reviewStatus` | `unreviewed` / `in_review` / `deferred` / **`done`** |
| `confirmPriority` | `focus` / `normal` / `parked` |
| `reviewDueAt` | 確認期日の設定・延長・解除 |
| `archivedAt` | 重複・誤起票のアーカイブ |
| メモ追記 | 整理理由の一言（既存の追記案と統合可） |

整理の典型パターン:

- 重複 → 1 件に寄せ、他をアーカイブまたは `done`
- もう追わなくてよい → `done`
- 残すが今ではない → `parked` / `deferred` ＋必要なら期日
- 今日見るべき少数 → `focus`（件数上限はプロンプトで指示してよい）

---

## 5. 反映の契約（HITL）

```text
EM: 「提案を整理して」（観点があれば添える）
  → Lead が既存提案を読む（注入＋ lookup）
  → 差分リスト（suggestion_updates 相当）を出力
  → UI で差分一覧（ID・変更前後・理由）
  → EM が「まとめて反映」で本体へ書き込み
  → 監査用に当該 Run に残す
```

| 段階 | 主体 | 内容 |
|---|---|---|
| Suggest | AI | 既存 ID 付きの変更案。根拠（なぜその帯／状態か）を添える |
| Decide | EM | 差分を一度見て、一括反映または却下／続きの壁打ち |
| 本体更新 | アプリ | 「まとめて反映」時のみ Suggestion を更新 |

項目ごとの個別採用は必須としない（整理は件数が多い前提のため）。  
**相談完了＝即書き込み**にはしない（依頼は明示でも、結果の目視と一括反映を残す）。

---

## 6. 既存経路との切り分け

| 経路 | 本方針との関係 |
|---|---|
| 新規「提案として残す」 | 維持。本方針の対象外（新規作成） |
| 他提案へのメモ追記案 | 維持。整理差分と併記してよい |
| `recommendation: dismiss` の Journal 自動却下 | 維持。**相談 Run／提案本体の状態変更とは別** |
| 提案更新分析（`auto-issue-update`） | **触らない**（依頼なしの書き換え経路にしない） |
| 旧 Issue 優先度提案（削除済み） | 復活させない。Suggestion 向けの整理差分として新設する |

---

## 7. 実装時の置き場（メモ・未着手）

実装は本ドキュメントの範囲外。着手時の手がかりのみ記す。

- エージェント出力: 既存の `issue_note` / `proposal` に加え、既存提案 ID 向けの更新ブロック（名称は実装時に決定）
- 採用 API: Run 単位の一括反映（部分 indices は任意）
- UI: 相談右パネル（`ConsultReviewPanel` 周辺）に差分一覧＋「まとめて反映」
- プロンプト: 整理依頼時に「今日の focus 上限」「done / アーカイブの使い分け」を明示

---

## 8. 一言まとめ

**既存提案の状態整理は、相談で頼んだときだけ AI に任せ、変更種類は制限せず（done 含む）、反映は「まとめて反映」1 回。裏での自動書き換えはしない。**
