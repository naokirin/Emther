# Emther（EM Support System・エージェント駆動型EMサポートシステム） UI/UX設計書（v4）

## 1. UXコンセプト：透明性と協働のワークスペース

本システムは、EMのための「コックピット」であり、AIと協働して思考を深める「ワークスペース」です。v4では以下のコンセプトを中核に据えています。

* **Explainability & Transparency (説明責任と透明性):** エージェントの「思考ログ」と「現在の状態シグナル」をリアルタイムに可視化し、ブラックボックス化を防ぎます。
* **Context Boundary (文脈の境界):** 組織の「不変のルール（憲法）」をツリー構造で管理し、日々の「揺らぎ（ログ）」と厳格に分離することで、AIのハルシネーションを抑止します。
* **Interactive Copilot (対話型協働):** Issueごとにコンテキストを共有したAIとチャットで壁打ちを行い、動的に計画をアップデートします。
* **Human-in-the-Loop & Cost Control:** エージェントは自律的に考えますが、重要な決断や情報不足時には必ず「Yield（一時停止）」し、EMの判断を仰ぐことで無駄なAIコストと暴走を防ぎます。
* **State Legibility（状態の可読性、「わからない」を隠さない）:** チームや組織の状態を「良い／悪い」の二値で無理に判定せず、判断材料が不足している場合は「評価不能」として明示します。データが無いことを暗黙的に「問題なし」と誤読させないための、EM向けの三値ステータス設計です。

## 2. EMの日常業務フローとシステム接点

| 時間帯 | EMの行動 | システム上のUX | 
| ----- | ----- | ----- | 
| **朝 (始業時)** | 全体把握・計画確認 | **ダッシュボード**を開き、最上部の**Team Vitals**でチームの状態（良好／要注意／評価不能）を数秒で把握。次にトリアージ待ちのInboxを確認し、**ステータスシグナル**で「🟡 Waiting (人間の入力待ち)」になっているエージェントがないか確認し、判断を下す。 | 
| **日中** | 1on1、会議、トラブル対応 | **クイックジャーナル**にメモを投下。裏側で軽量モデルが即座に `#タグ` や `@人名` を自動付与し、整理の手間を省く。 | 
| **適時** | 組織方針の策定・Issue解決 | **Issue Workspace**を開き、AIと「壁打ち（Copilotチャット）」を行い、方針を固めて計画（State）を更新する。 | 
| **期初/適時** | 組織の前提条件の更新 | **Organization Context**のディレクトリツリーを編集し、チーム体制やミッションの変更を反映させる。 | 

## 3. 主要4画面のUX仕様とインターフェース設計

### 3.1 統合ダッシュボード（Home & Triage）

日々のトリアージと、システムの「心臓部（エージェント群）」の監視を行うメイン画面。

* **最上部 (Team Vitals Bar):** 画面を開いて最初に目に入る、チーム・組織の健全性バイタル表示帯。詳細は3.1.1参照。
* **左ペイン (グローバルナビゲーション & Agent Status):**
  * メニュー: Inbox / Issues / Journal / Organization Context
  * **Agent Status シグナル:** 各エージェントの稼働状況が一目でわかる信号機UI。
    * `🟢 Active (稼働中)`: Lead Agent
    * `🟡 Yield (入力待ち)`: Process Agent (Issue #42の解決案承認待ち)
    * `⚪️ Idle (待機)`: People Agent
    * `🔴 Error`: Tech Agent

* **中央ペイン (AI Inbox - トリアージ待ち):**
  * エージェントからの「ドラフトIssue」「ピボット提案」「リスクアラート」がカード状に並ぶ。
  * カードには「結論」「参照ファクト」「推論ロジック」がサマリー表示される。

* **右ペイン (Agent Activity Stream):**
  * バックグラウンドで動くエージェント（CLIプロセス）の標準出力をターミナル風にストリーミング表示する。
  * `[People Agent] 📖 Team Bの1on1ログを読み込み中...`
  * `[Process Agent] ⚠️ Yield: 経営陣の今期予算制約の情報が不足しています。EMの入力を待機します。`

#### 3.1.1 Team Vitals（チーム健全性バイタル）

ダッシュボード最上部に常設する、チーム・組織の状態を数秒で把握するための帯状ウィジェット。Agent Statusが「AIエージェントの稼働状況」を示すのに対し、Team Vitalsは「組織・チームそのものの健全性」を示すものであり、目的が異なる。

* **三値ステータス:** 各バイタルは以下の3状態のいずれかを取る。二値（良い/悪い）ではなく、意図的に3値とすることで「判断材料が無いこと」自体を可視化する。
  * `🟢 安定/良好`: 直近のログ・メトリクスに基づき健全と判定できる状態（例: `Team A: 🟢 安定 (+2%)`）。
  * `🟡 要注意 / 🔴 危険`: 閾値を下回る、または悪化トレンドが検知された状態（例: `Team B: 🟡 低下 (-15%)`）。数値の悪化度合いに応じて🟡/🔴を切り替える。
  * `⚪️ 評価不能`: 判定に必要なデータ（ジャーナル、1on1ログ等）が一定期間内に存在せず、AIが安全に判定できない状態（例: `Team C: ⚪️ 評価不能 (情報不足)`）。**この状態を「問題なし」の🟢や、単なる待機を示すAgent Statusの⚪️ Idleと混同させないことが最重要要件**であり、必ず「評価不能」「情報不足」等の文言を併記し、カード自体も破線枠など視覚的に区別したスタイルで表示する。
* **クリックによる根拠開示 (Explainability連動):** 各バイタルカードをクリックすると、判定根拠（参照した期間・データソース）または評価不能の理由（例:「過去30日間、Team Cの1on1ログ・ジャーナル入力が0件」）がポップオーバーで表示される。「なんとなく悪い/良い」ではなく、常に参照可能なファクトに基づく。
* **閾値の設定:** 🟢/🟡/🔴の閾値やデータ欠如とみなす期間は、Organization Contextの`Rules_and_Constraints`配下で組織ごとに定義し、AIの独断で変動させない。
* **チーム単位以外のバイタル例:**
  * `1on1 Coverage (30日): 4/5` — 直近30日以内に1on1が実施されたメンバー比率。
  * `今期目標 15/33 完了 🔴` — OKR/目標の進捗率とその健全性シグナル。
* この設計により、EMは「良い」「悪い」「まだ見えていない」の3つを瞬時に切り分けられ、「見えていないのに安心してしまう」事故を防ぐ。

### 3.2 Organization Context（組織の憲法・前提管理）

AIが思考する際の「絶対的な前提」を管理する画面。明確な境界を持つディレクトリ構造として表現する。

* **ツリー構造ナビゲーション (左側):**
  * `📁 Strategy` (全社MVV, 今期OKR)
  * `📁 Teams` > `📁 Team_A` (ミッション, メンバー)
  * `📁 Rules_and_Constraints`
* **構造化エディタ (右側):**
  * ノードを選択すると、JSON/YAMLライクな構造化フォームが開き情報を編集できる。
* この構造により、AIは関連する Issue の処理時に必要なディレクトリ配下**だけ**を「動的ロード」し、思考のブレを防ぐ。

### 3.3 クイックジャーナル（インプット・ウィジェット）

日々の「揺らぎ」や「スポット情報」を収集する低摩擦なデジタルノート。

* **入力エリア:** 主語のない短いメモや感情の吐露を許容。
* **軽量モデルによる自動タグ付け (Ingestion UI):**
  * EMが「今日のCさんとの1on1、リファクタリングが進まず疲弊気味だった」と入力しSubmitすると、瞬時にUI上に抽出結果が表示される。
  * `抽出完了: @Cさん, #技術的負債, #モチベーション低下, [Urgency: Medium]`
  * EMはこの自動抽出結果を微修正して保存可能。これにより後からAIも人間も容易に分類・検索が可能になる。

### 3.4 Issue Workspace (Issue詳細＆壁打ちボード) 

課題の解像度を上げ、実行計画をAIと「協働編集」する2ペイン画面。

* **左ペイン：Issue State（現在の状態と計画）**
  * サマリー、関連ナレッジ（自動タグ付けされたジャーナル等へのリンク）、動的ロードマップ（タスク一覧）。

* **右ペイン：Copilot Chat（インタラクティブな壁打ち）**
  * CLIのインタラクティブモード（REPL）と標準入出力で接続された対話インターフェース。
  * **Yield（一時停止）と承認のアクション:**
    * AIが「A案（リスケジュール）」と「B案（人員補充）」を提示した際、プロセスのステータスは `🟡 Yield` となる。
    * チャットUI上に「💡 プランを更新しますか？」というアクションカード（A案を採用 / B案を採用 / 却下して相談を続ける）が表示される。
    * EMがボタンを押すとState（左ペイン）が更新され、エージェントは `🟢 Active` に戻り次のタスク分解へと進む。
