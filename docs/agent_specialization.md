# エージェント専門性の差分化（役割・観点・コンテキスト）

作成日: 2026-09-08  
関連: `docs/first_implession/em_v5.md` / `docs/improvement_v1.md`（F） / `docs/em_human_story_and_ux.md` / `docs/memo.md`  
対象コード: `web/src/lib/agent-runtime.ts`（`buildSystemPrompt`） / `web/src/lib/types.ts`（`AGENT_OPTIONS` / `INTERVENTION_TYPES`）

---

## 0. 位置づけと結論

EM支援における AI エージェントチームについて:

- **編成・オーケストレーション（Lead＋4象限＋consult）は適切**
- **各エージェントの専門性は「設計されている」と言うには足りず、モデルの名前推論に委ねている**

専門チームとしての信頼性を上げる次の一手は、自律度やエージェント数を増やすことではなく、**役割定義と観点・コンテキストの差分化**である。

差分化の目的は、**同じ事実に対して再現可能に違う切り口を返すこと**である。

---

## 1. 現状（何が専門性を決めているか）

### 1.1 コード上の差（実質これだけ）

| 要素 | Lead | People / Process / Tech / Product |
|---|---|---|
| システムプロンプトの自己紹介 | `「Lead Agent」` | `「〇〇 Agent」`（名前のみ） |
| consult 可否 | あり（並列可・1ターン1回） | なし |
| proposal / yield 形式 | 共通 | 共通 |
| 注入コンテキスト（MVV・Objectives・チーム・Issue・Journal） | 共通 | 共通 |
| 役割別の「見るべき観点」段落 | **無し** | **無し** |

核心は `buildSystemPrompt` 内の次の形である。

```
あなたはEM支援システムの一部として動作する「${agentName}」です。
```

`docs/memo.md` の大規模改善 F 実装メモでも、People/Process/Tech にも役割説明は無く、Product も同じ方式（名前推論）に揃えたと明記されている。

### 1.2 運用・導線上の差

| エージェント | 主な起動経路 |
|---|---|
| Lead | 相談、異常検知、朝サマリー、手動 |
| People | 手動、consult、プロファイル下書き |
| Process / Tech / Product | 手動、consult |

「誰を呼ぶか」の配線はあるが、「呼んだあとに何を専門とするか」の仕様はほぼ名前頼みである。

### 1.3 判定まとめ

| 観点 | 判定 |
|---|---|
| 4象限の欠けが無いか | 適切（Product 含む） |
| Leadが統括し専門家に分業できるか | 仕組みは適切 |
| 各エージェントが異なるレンズで見るか | 設計としては弱い |
| 専門に応じた知識の渡し分け | 弱い |
| EMが用途を誤認しにくいか | 中程度 |

## 2. 差分化の3層

| 層 | 意味 | いま | 目指す状態 |
|---|---|---|---|
| **A. 役割定義** | 「何者で、何を専門とし、何を専門としないか」 | 名前1行 | 短い固定ブロック（3〜8行） |
| **B. 観点（レンズ）** | 提案時に必ず見る／書かないチェックリスト | 無し | proposal の `logic` / `facts` の質を誘導 |
| **C. コンテキスト** | 渡す前提情報の厚み・種類 | ほぼ共通 | 共通コア＋象限の「厚み加算」（完全分離はしない） |

完全に別プロンプト・別ナレッジにすると、Lead の統合が難しくなりコストも増える。  
方針は **共通の出力規約（proposal/yield）は維持し、中身のレンズと材料だけ差をつける** こと。

---

## 3. A. 役割定義（各エージェントに足す文面の骨格）

実装イメージ: `buildSystemPrompt` で `agentName` ごとに `ROLE_BLOCK[agentName]` を、自己紹介の直後に挿入する。

### 3.1 共通の枠（専門エージェント）

```
【役割】
- 専門領域: …
- 主に答える問い: …
- やらないこと: …（他象限へ寄せすぎない／Leadに返す）
- 提案の翻訳先: 組織介入（人・仕組み・優先順位）。実装チケットの羅列に落とさない
- 情報不足時: 推測で埋めず yield（options 空可）
```

**「やらないこと」を必ず書く。** 専門性は肯定文より境界で安定する。

### 3.2 Lead Agent

```
【役割】
- 専門領域: 論点の分解、専門エージェントへの振り分け、統合判断、EMへのYield
- 主に答える問い: 「今日EMが決めるべきことは何か／誰の専門見解が必要か」
- やらないこと: 一象限の深い専門分析を自分だけで完結させること（必要ならconsult）
- 統合時: 専門家の一致点・相違点・採用した軸を logic に明示する
- コスト: 無関係なconsultを増やさない
```

### 3.3 People Agent

```
【役割】
- 専門領域: 個人・関係性・動機・成長・心理的安全性・1on1・オンボーディング
- 主に答える問い: 「誰の状態がどう変化し、EMは人にどう介入すべきか」
- 見る: 人物プロファイル、Journalの感情・緊急度、チーム内の関係・負荷の偏り
- やらないこと: 技術選定の本論、ロードマップ優先順位の本論（必要なら境界を示す）
- 提案の翻訳先: 1on1設計、心理的安全性、役割の人側、採用・オンボーディング
```

### 3.4 Process Agent

```
【役割】
- 専門領域: 意思決定、フロー、依存、会議体、エスカレーション、プロセス変更
- 主に答える問い: 「仕事がどこで止まり、仕組みとしてどう直すか」
- 見る: 手戻り／待ち／承認の所在、チーム間依存、運用ルールと実態の乖離
- やらないこと: 個人の内面の深掘り（People）、顧客価値の優先の本論（Product）
- 提案の翻訳先: 意思決定プロセス、依存関係の切り方、プロセス変更、役割明確化（責任の置き方）
```

### 3.5 Tech Agent

```
【役割】
- 専門領域: 技術的負債、品質、アーキ制約、リリースリスク、実装可能性が組織に与える摩擦
- 主に答える問い: 「技術制約が組織のどこを詰まらせているか／EMが調整すべき技術−組織の接点は何か」
- 見る: 負債・障害・リリース遅延の技術要因、専門性の偏り、ツール／環境のボトルネック
- やらないこと: コードを書く、リポジトリ操作（ツール無効）。純粋な人事評価の本論
- 提案の翻訳先: 依存の技術境界、プロセス（リリース／レビュー）、優先順位（返済 vs 機能）へのインプット
- 注意: 「実装タスク一覧」ではなく「組織障害としての技術」で語る
```

### 3.6 Product Agent

```
【役割】
- 専門領域: 顧客価値、優先順位、スコープ、ロードマップと組織能力の齟齬
- 主に答える問い: 「何をやる／やらないべきで、それが組織のどこと衝突しているか」
- 見る: Objective/KR、並行過多、スコープ膨張、価値に対する組織の供給能力
- やらないこと: 個人のケアの本論（People）、詳細な技術設計（Tech）
- 提案の翻訳先: 優先順位／スコープ、役割・意思決定（優先の決まる場所）、プロセス（価値検証の回し方）
```

## 4. B. 観点チェックリスト

役割定義の下に、象限ごとの必須観点（3つ前後）を置く。

| Agent | logic / facts で触れること | 触れなくてよいこと |
|---|---|---|
| People | 誰か、状態変化、関係・負荷、介入は「対話／配置／支援」のどれか | 技術スタック選定の詳細 |
| Process | 止まる工程、決まる場所の有無、依存の向き、変更の最小単位 | 個人の性格診断 |
| Tech | 技術要因→組織影響の因果、返済／回避の選択肢、EMが動かすレバー | パッチコード |
| Product | 価値仮説、KRとの関係、やらないこと、組織供給とのギャップ | 1on1スクリプトの詳細 |
| Lead | 争点の整理、consult要否、EMが今日決める1点 | 一象限の百科事典的解説 |

共通ルール（現状の proposal 形式はそのまま）:

- `facts` は注入された前提・Journalから。無いものは作らない
- 他象限が本質なら、無理に自象限で完結せず「○○ Agent の見解が必要」と logic に書く（Leadなら consult、専門なら境界明示）

## 5. C. コンテキストの差分化（厚み加算）

### 5.1 原則

- **削りすぎない**: 手がかりが無いのに情報を隠すと誤判断が増える（既存のチーム名簿フォールバック思想と同じ）
- **足し方で差をつける**: 共通コアは全エージェントに渡し、象限ごとに「強調ブロック」を追加
- **完全な専用ナレッジDBは、この段階では作らない**

### 5.2 共通コア（現状維持でよい）

- MVV（Strategy）
- Objectives/KR（タイトル程度）
- 関連チーム名簿（既存の絞り込み）
- Issue charter / チーム憲法（紐付き時）
- 言及に応じた Journal／解釈（現状の動的ロード）

### 5.3 象限ごとの厚み

| Agent | 厚くする | 薄くてよい／参考扱いと明示 |
|---|---|---|
| People | 言及人物の解釈（長期プロファイル）を多め、直近 Journal の sentiment/urgency、Peopleハブ相当の要約 | Objectives全文の詳細進捗 |
| Process | チーム憲法（mission/constraints）、関連Issueのプロセス系タグ／介入型、依存が読み取れる charter | 個人解釈の長文すべて |
| Tech | 技術・障害・負債に触れる Journal／Issue文、関連チーム制約 | 人物性格の深掘り |
| Product | Objectives/KR一覧を「判断の主軸」と明示、優先順位／スコープ系タグ、KR紐付きの有無 | 1on1ログの詳細 |
| Lead | 現状の共通セット＋「不足している象限情報」を自分で見抜く指示 | 専門家並みの一分野深掘りを強制しない |

実装の置き方の例（既存関数の延長）:

- `buildJournalContextBlock` に `agentName` を渡し、People なら interpretation を優先・件数増
- `buildObjectivesBlock` の前置き文を Product/Lead では「優先判断の主軸」、People では「参考」に変える
- Issue `tags` が介入の型を含むなら、該当象限のときに「この介入型を前提にせよ」と1行足す

**やらない方がよい差分化:** エージェントごとに全く違う事実セットを渡し、Leadが統合不能になること。

## 6. Lead の consult 差分化（振り分け表）

現状の「名前列挙＋コスト注意」を、振り分けヒューリスティックに置き換える。

| 論点の兆し | 呼ぶ先 |
|---|---|
| 特定人物・モチベ・1on1・安全性・オンボード | People |
| 承認待ち・会議・フロー・手戻り・依存 | Process |
| 障害・負債・リリース技術要因・スキル偏り（技術） | Tech |
| 優先順位・スコープ・KR・顧客価値・ロードマップ衝突 | Product |
| 人×プロセス、技術×優先など複合 | 該当2つまで（3つ以上は例外） |

consult の `question` について:

- 同じ長文タスクを丸投げしない
- 「Peopleには人物面だけ、Processには流れの詰まりだけ」と Lead が問いを切るよう指示する
- 現状実装は同一 `question` を全 specialist に送るため、**まずはプロンプトで「問いを専門向けに一文で書け」を強化**し、将来必要なら agents ごとに question を分ける

## 7. 介入の型 ↔ エージェント（既存資産の接続）

`INTERVENTION_TYPES`（`types.ts`）はすでにEM言語としてあるので、エージェント差分化の辞書に使う。

| 介入の型 | 主担当 | 副 |
|---|---|---|
| 1on1設計 / 心理的安全性 / 採用・オンボーディング | People | Process |
| 意思決定プロセス / プロセス変更 / 依存関係の切り方 | Process | Tech（技術依存時） |
| 優先順位／スコープ | Product | Process |
| 役割明確化 | Process + People | — |

使い方:

1. Issueに型タグがある → 紐付き Run の専門エージェントに「この介入型を主軸に」
2. Lead の consult 選択のヒントに同じ表を載せる
3. UIのエージェント選択に一行ヒント（「人・関係」「流れ・決裁」等）— プロンプト以外の差分化

コードとプロンプトとUIが同じ辞書を共有すると、専門チーム感が一気に出る。

---

## 8. 実装上の置き場

変更の中心はほぼ `buildSystemPrompt` 周辺で足りる。新画面・新エージェント種別は不要。Settings も基本不要（プロンプト定数でよい）。

```
base =
  自己紹介(名前)
  + ROLE_BLOCK[agentName]          ← 新規
  + VIEWPOINT_CHECKLIST[agentName] ← 新規（任意だが推奨）
  + 共通ルール(proposal/yield)
  + consultRule（Leadのみ・振り分け表を厚く）
  + action_items / sub_issues（既存）
  + contexts（共通＋agentNameで厚み調整）
```

---

## 9. 成功条件

同じタスク例で、専門家の `conclusion` / `logic` の軸が違うこと。

例: 「リリースが遅れ、メンバーが疲弊している」

| Agent | 期待される主軸 |
|---|---|
| People | 疲弊・関係・1on1・負荷の人側 |
| Process | リリースプロセス・承認・依存の流れ |
| Tech | 技術的ボトルネック・品質ゲート |
| Product | スコープ過多・KRとの衝突・やらないことの欠如 |
| Lead | 上記を統合し、EMが今日決める一点＋必要なら並列consult |

逆に全部が「コミュニケーションを改善しましょう」なら、差分化失敗。

コスト面の成功条件:

- 無関係4体consultが減る
- 必要な2体consultの回答が重複せず統合しやすい

## 10. 段階的な進め方

| 段階 | 内容 | 効果 |
|---|---|---|
| **1** | ROLE_BLOCK＋やらないこと（全文短い） | 役割崩壊の抑制（最小コスト） |
| **2** | Leadの振り分け表＋介入型対応表 | consultの適切さ・コスト |
| **3** | 観点チェックリスト | proposalの再現性 |
| **4** | コンテキスト厚みの差（People解釈多め等） | 材料面の専門性 |
| **5** | （任意）consultの question をエージェント別に分割 | さらに分業精度 |

1→2だけでも「専門チームらしさ」はかなり上がる。4はデータ経路の変更がいるので後段が安全。

---

## 11. やらないこと（差分化の失敗モード）

- 長いペルソナ小説（ノイズ・トークン増・指示無視）
- エージェントごとに矛盾する絶対前提を渡す
- Techに「コードを書け」とツールを戻す（EM組織支援から逸脱）
- 差分化のために自動起動や連続ターンを増やす（忙殺・コスト問題の再燃）
- UI上のエージェントを増やして象限を細分化しすぎる（先にレンズを固定）

---

## 12. まとめ

差分化とは次の三点セットである。

1. **役割定義** — 専門と非専門の境界を短く固定する  
2. **観点** — 提案時に必ず通すレンズを象限ごとに固定する  
3. **コンテキスト** — 同じコアに、象限向けの厚みだけ足す  

これに **Leadの振り分け表** と既存の **介入の型** を接続すると、現状の「名前だけの5エージェント」が、EMの4象限を実際に分担するチームに近づく。

自律度を上げるより先にやるべきなのは、この再現可能な切り口の設計である。
