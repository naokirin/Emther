# EM Support System: UI/UX改善およびIssue進捗管理 要件定義

関連: `docs/em_human_story_and_ux.md` / `docs/agent_specialization.md` / `docs/dashboard_ui_readability.md`  
方針決定（2026-09-08）: トリアージはAI主導（EMは例外上書き）／計画の本体反映あり／人・優先順位に触れる介入は常にYield

---

## 1. 目的と背景

現状のダッシュボードは「情報のデータベース（名詞ベースのタブ構造）」となっており、Engineering Manager（EM）の実際の業務フロー（朝・日中・終業時）と合致していないため、認知負荷が高い。
また、AIエージェントの動作状態が不透明であること、および「Issue化された課題が実際に進行しているか」を俯瞰・管理する機能が不足している。

本要件定義の目的は次の3点である。

1. EMの行動に寄り添う動的なUIへの改修
2. AIの透明性向上と、自律／通知／判断待ちの責任分界の明示
3. タスク管理ライクなIssue進捗ビューの実装

成功状態の一文:

> AIが分析・発見・整理・トリアージ・計画立案・監視を自律実行し、EMには優先度付きの判断点と介入トリガーだけが届く。

---

## 2. AI自律境界とEM接点（設計の中核）

UI改修はすべて本節の契約に従う。画面に「全部出す」ことは自律の成功ではない。自律の成果は原則ログに残し、EM向けUIは判断と介入に必要な最小面だけを映す。

### 2.1 動作モード

| モード | 意味 | EMへの露出 |
|---|---|---|
| **Autonomous** | AIが完結。結果は履歴に残す | 原則見せない（後追い可能なタイムライン） |
| **Notify** | AIが結論まで出し、EMは「知る／無視できる」 | 圧縮1行〜短いサマリー。アクション必須ではない |
| **Yield** | EMの判断・情報・コミットなしに進めない | 朝の最上部など、意図的に邪魔する |
| **EM Trigger** | 人間が起動する壁打ち・手動Run・憲法更新 | 日中の常設導線（Journal／相談） |

### 2.2 業務パイプライン上の責任分界

| 工程 | モード | 方針 |
|---|---|---|
| 現状分析（Journal／Vitals／Run結果の集約） | Autonomous | 常時。朝は「組織の一文」だけ表面化 |
| 課題の発見 | Autonomous → 閾値超で Notify | ドラフト起票まで自動。候補を全部Inboxに載せない |
| 課題の整理（Why/What/How、関連付け、低リスク補完） | Autonomous（本体反映あり） | 埋められる項目は本体へ自動適用。戦略・人事に触れる記述は案のまま残し Yield または確認可能な差分にする |
| トリアージ（今やる／様子見／捨てる） | **Autonomous 主導** | AIが毎日「今日の組織の問い」と判断候補を **上限N件（目安: 判断3＋観測任意）** に圧縮。EMは例外時のみ上書き・却下・昇格 |
| 計画立案（Action Items／子Issue） | Autonomous（本体反映あり） | 一定条件を満たす提案は Issue 本体へ自動反映。新規介入型・高リスク分解のみ Yield |
| 停滞・異常の監視 | Autonomous → 再トリアージ材料 | ハイライト一覧を増やさない。「今日のN件に食い込む資格があるか」の再評価入力にする |
| EMへのアラート | Notify（希少）／Yield（稀） | 緊急度×可逆性×説明責任で格上げ。アクセント色はここだけ |
| 介入の実行（人を動かす・優先順位を変える・外部コミット） | **常に Yield または EM Trigger** | 組織への働きかけの最終決定と説明責任は人間EM |
| 振り返り・効果判定 | Autonomous → 週次 Notify | 日次でEMに読ませない |

### 2.3 Yield の種類（UI契約）

既存の「選択肢／情報不足」を、画面上は次の種別に分けて扱う。

| 種別 | EMがやること | 朝の最上段 |
|---|---|---|
| **Decide** | 複数案から選ぶ | ○ |
| **Inform** | 足りない前提を足す | ○ |
| **Commit** | 介入を「やる」と決める／人に話す／優先を変える | ○ |
| **Triage override** | AIの「今日のN件」を上書きする | 任意（主作業ではなく例外） |

Morning Mode の Yield カードは Decide / Inform / Commit のみを載せる。分析・整理・停滞検知の生ログは載せない。

### 2.4 計画の本体反映ルール（方針）

- **自動反映してよい例:** 既存介入型の延長である具体Action Item、不足しているWhy/What/Howのうち事実から埋められる項目、既存Issueの機械的な関連付け
- **自動反映せず Yield する例:** 人の配置・評価・1on1方針に触れる案、他チーム／経営へのコミット、優先順位の入れ替え、新規の介入型や大きな子Issue分解
- 自動反映したものは必ず自律アクションのタイムラインに残し、EMが後から取り消せる

### 2.5 成果物の置き場

| 置き場 | 役割 |
|---|---|
| Dashboard（今日） | 判断と介入の最小面（問い1文＋Yield＋今日のN件） |
| Issue Workspace | 介入の作業面（計画・壁打ち・Commit） |
| タイムライン／通知領域 | 自律成果の監査ログ（情報過多の受け皿にしない） |
| Reports／週次 | 振り返りの Notify 面 |

### 2.6 成功指標（UX）

- 朝にEMが触る判断点の件数（目標: 数件以内）
- Yield率（過剰Yield＝自律不足、過少Yield＝暴走リスク）
- AIが様子見／再浮上スケジュールに回した課題数（人間キューを増やしていないか）
- 自動本体反映の取り消し率（ルール調整の信号）

## 3. フロー駆動型動的UIへの再構築（「今日」タブの改修）

タブの構造を見直し、デフォルト画面である「今日」タブを時間帯やEMのアクションに応じて変化させる。表示内容は §2 の契約に従い、Autonomous の生出力を並べない。

*   **Morning Mode (朝の確認とブロッカー排除)**
    *   **表示要素:** 「今日の組織の問い」1文、Decide/Inform/Commit の Yield カード（最上部）、AIが圧縮した本日の優先候補（上限N件）。前日サマリーや停滞検知はN件に食い込んだものだけ表面化。
    *   **目的:** AIが既に行ったトリアージ結果を確認し、判断待ちだけを最速で解消する。フルキュー編集を朝の主作業にしない。
*   **Daytime Mode (日中の記録と壁打ち)**
    *   **表示要素:** 「Quick Journal」と「AI相談チャット」（EM Trigger）を常にアクセスしやすい位置（フローティングや固定サイドバー等）に配置。
    *   **目的:** 思考を遮らずに発生事象をメモし、必要なときだけ壁打ち・介入トリガーを起動できる状態を維持する。
*   **Evening Mode (終業時の振り返り)**
    *   **表示要素:** 「EM自身のバイタル入力」と、AIが生成した「本日の進行状況サマリー（完了・残・自動反映件数等）」の短い Notify。詳細はタイムラインへ。
    *   **目的:** 認知リソースを使わずに1日を締めくくる。

## 4. Issue進捗管理ビューの実装（新規/拡張要件）

Issueが「起票されただけ」になるのを防ぎ、進行状況をひと目で把握するためのビューを追加する。進捗ビューは主に **AIの自律ループのセンサーと作業面** であり、朝のDashboardに生の停滞一覧を増やす用途ではない（§2.2）。

*   **ビューの切り替え機能 (View Toggle)**
    *   現在の「Issue一覧（リスト）」に加え、進行状況を管理しやすい「カンバンビュー (Board)」または「プログレスビュー (Timeline/Gantt)」への切り替えボタンを実装する。
*   **ステータス管理の導入**
    *   各Issueにステータスを持たせる（例: `未着手`, `進行中`, `ブロッカーあり(Waiting)`, `完了`）。
*   **進捗の視覚化**
    *   リストビューにおいても、サブIssueの消化率やAction Itemの完了数をもとにした「進捗プログレスバー」を表示する。
*   **AIによる進捗アシスト (Stalled Issue Detection)**
    *   一定期間（例: 3日間）進捗がない、またはAction Itemが追加されていないIssueをAIが検知する。
    *   検知結果はまず Autonomous の再トリアージ材料とし、今日のN件に昇格した場合のみ Morning Mode / Notify に載せる。滞留一覧の常時掲示はしない。

## 5. AIエージェントの透明性と状態の可視化

AIが背後で何をしているのかをEMが直感的に理解できるようにする。透明性は「全部見せる」ではなく、「今どのモードで動いているか」と「なぜYieldしたか」が分かることである。

*   **処理中ステータスの明示**
    *   AIがバックグラウンドで処理を行っている際、「分析中…（1on1ログを解析しています）」といった具体的なコンテキストを伴うインジケーター（スピナーやプログレスバー）を表示する。
*   **Yield（判断待ち）UIの改善**
    *   テキストの羅列ではなく、独立したカードUIにする（Decide / Inform / Commit を明示）。
    *   「なぜEMの判断が必要なのか（不足している情報やリスク・不可逆性）」をカードのヘッダーにハイライトして表示する。
*   **自律アクションのタイムライン化**
    *   AIが自動で行った整理・トリアージ圧縮・計画の本体反映（例: 「メモからIssueを自動生成」「Why/What/Howを補完して本体反映」「今日の候補を3件に圧縮」）は、監査用の履歴としてタイムラインまたは通知領域に表示する。Dashboardの主面には載せない。

---

## 6. 視覚的階層とコントラストの改善（ダークテーマ最適化）

情報が平坦に見える課題を解決するため、UIのレイヤー（深度）を定義する。視線の最初の着地は §2 の Yield と今日のN件に固定する。

*   **エレベーション（階層）の適用**
    *   背景（最も暗い色）と、カードコンポーネント（少し明るい色）のコントラスト差を広げ、境界線を明確にする（微妙なボーダーやシャドウの活用）。
*   **アクセントカラーの戦略的配置**
    *   最も重要なアクション（Urgency: High、Yieldの承認／Commit、今日のN件に食い込んだ Notify）にのみ、赤やオレンジなどの視線を惹きつけるアクセントカラーを使用し、それ以外（自律ログ・副次パネル）は彩度を落とす。

---

## 7. 閲覧ビューと編集ビューの分離（可読性の向上）

AIが分析・整理したテキストや、過去の記録を「読む」体験を阻害しないよう、UIのデフォルト状態を最適化する。

閲覧モード（Read-Only View）のデフォルト化

Issueの詳細（Why/What/How等）やJournalの内容は、デフォルトで入力フォームを持たない「閲覧モード」として表示する。

テキストはMarkdownとして美しくレンダリングし、見出し、箇条書き、太字などを活かして視認性を高める。

入力枠やプレースホルダーによる視覚的ノイズを排除する。

シームレスな編集モード（Edit Mode）への移行

閲覧状態のテキスト領域をクリック（または「編集」アイコンをクリック）することで、インラインまたはモーダルで素早く「編集モード（現状の入力フォーム）」に切り替わるようにする。

編集が完了（保存またはフォーカスが外れる）すると、即座に閲覧モードに戻る仕様とする。
