# 個人・機密情報チェック：一般解の調査メモ

作成日: 2026-09-13  
性質: **調査メモ**（実装決定の正本ではない）  
関連: `docs/privacy_check.md`、`web/src/lib/mask-check-lexicon.ts`（CORE / TUNING）

---

## 0. なぜ調べるか

ローカル完結の PII／機密検知は一般的な課題だが、現状の Emther 実装は検証テキスト由来の TUNING（長い言い回し・除外語の積み上げ）が効いている。  
結論を急がず、健全で具体的な既存解を押さえてからアーキテクチャを見直す。

---

## 1. 業界定石（層の分離）

| 層 | 対象 | 定番 | Emther 現状 |
|---|---|---|---|
| A. 構造化実値 | メール・電話・鍵文字列 | regex＋checksum／エントロピー | `LITERAL_PATTERNS`（健全） |
| B. 秘密実体 | APIキー本体 | Gitleaks 系 | `api_key_like`（言及と混ぜない方がよい） |
| C. 人名など | 氏名 | NER（spaCy / GiNZA）＋後処理 | 敬称／話者／カタカナ規則＋SLM フィルタ |
| D. 機微「話題」 | 「漏洩の話」など | 短い核キーワード or 分類／LLM | CORE＋TUNING フレーズ（TUNING が過適合寄り） |

共通メッセージ:

- 自動化に完全保証はない（Presidio も明記）
- **1手法に寄せない**（Recognizer／層の合成）
- deny-list / allow-list / コンテキストでスコア調整が本番ではほぼ必須
- LLM は補助。本線を LLM＋長いルール羅列にしない

## 2. 参照すべき具体物

### Microsoft Presidio

- ローカル PII 検知＋匿名化。Recognizer 差し替え（regex / NER / deny-list / ローカル LLM）
- 設計の型として最有力（「フレーズを足す」より「Recognizer 単位」）
- 日本語は spaCy/GiNZA ＋言語別 Recognizer 追加が前提  
  - https://github.com/Microsoft/presidio  
  - https://microsoft.github.io/presidio/analyzer/languages/

### GiNZA（日本語 NER）

- ローカル。`Person` 等
- 実務事例はほぼ **NER（氏名）＋ regex（電話・郵便・メール）**
- 素精度は不足しがち → 追加学習・負例・deny-list がよく出る  
  - https://megagonlabs.github.io/ginza/

### 秘密スキャン（Gitleaks 等）

- 鍵**実体**向け。PII／「機微な話題」とは別問題

## 5. 測定結果（2026-09-13）— GiNZA vs Emther 人名

環境: `ja_ginza` 5.2 / spaCy 3.8、フィクスチャは実検証で使った2本（`incident_mtg` / `release_standup`）。  
スコアは敬称を除いた正規化名での P/R/F1。ゴールドは長い敬称形を優先（例: `中村一郎さん` のみ、短い `中村さん` は載せない）。

| サンプル | エンジン | P | R | F1 | FP（正規化） | FN（正規化） |
|---|---|---:|---:|---:|---|---|
| incident_mtg | Emther ルール | 1.00 | 1.00 | 1.00 | — | — |
| incident_mtg | GiNZA Person | 0.875 | 0.875 | 0.875 | `し` | `ただとし` |
| release_standup | Emther ルール | 1.00 | 1.00 | 1.00 | — | — |
| release_standup | GiNZA Person | 1.00 | 1.00 | 1.00 | — | — |

観察:

- **漢字姓＋フルネームは GiNZA が十分強い**（リリース定例は完全一致）。`さん` は `Title_Other` に分かれ、Person は bare 名。
- **ひらがな名は GiNZA が弱い**: `ただとしさん` を Person として取れず、断片の `し` を Person にする誤検知が出た。Emther は敬称ルールで拾える。
- Emther がこの2本で満点なのは、**敬称構造＋（必要なら）TUNING 除外**がサンプルに効いているため。汎化保証ではない。
- GiNZA のノイズ例（人名以外）: `Azure`→Car、`Slack`→Doctrine、`議事録`→Constellation など。Person フィルタを掛ければ人名比較では除外されるが、素の NER をそのまま使うのは危険。

結論（人名層 C）: **GiNZA 単独置換は早計**。漢字人名の本線候補にはなりうるが、ひらがな名・敬称議事録では Emther 側の構造ルール（または後処理）がなお必要。

## 6. TUNING → CORE 棚卸し（同フィクスチャ）

機微キーワードを CORE のみ / TUNING のみで走査（部分一致で「CORE に吸収済み」とみなす）。

### incident_mtg

| 区分 | ヒット例 |
|---|---|
| CORE で既に拾える | `APIキー`, `個人情報`, `漏洩`（→ TUNING の `個人情報の漏洩` / `漏洩を伴う` / `個人情報が一部` は吸収可） |
| TUNING 独自（CORE 未カバー） | `認証系`, `不正利用`, `不正に利用`, `アカウントが不正`, `アクセスを遮断`, `セキュリティインシデント`, `被害拡大`, `不審なアクセス` |

### release_standup

| 区分 | ヒット例 |
|---|---|
| CORE で十分 | `パスワード`, `認証情報`, `アクセスキー`, `個人情報`, `契約金額` |
| TUNING | **ヒットなし**（この文では TUNING フレーズが不要） |

吸収方針のメモ:

| TUNING | 判定 | 理由 |
|---|---|---|
| `個人情報の漏洩` 等 | **CORE に吸収済み扱い** | 核 `個人情報`/`漏洩` で足りる |
| `apiキー` | **CORE の大小無視で吸収可** | `APIキー` と同一 |
| `メンタル不調` / `年収交渉` | **CORE 核で足りる** | `メンタル` / `年収` |
| `不正アクセス` | **CORE 候補** | ドメイン横断でよく使う短核 |
| `不正利用` / `アカウントが不正` / `アクセスを遮断` / `被害拡大` / `不審なアクセス` / `認証系` / `セキュリティインシデント` | **TUNING のまま or 捨てて様子見** | インシデント議事録寄り。CORE に入れると一般文で FP 増 |
| 巨大カタカナ stopword | **辞書層として残す**が、**サンプル都度追加は止める** | 業界的にも deny-list は必要。増殖プロセスが問題 |
| `のアカウント` lookahead | **TUNING のまま** | `ただとしのアカウント` 専用に近い。GiNZA もここを落としている |

## 7. 測定後の判断

1. **人名**: GiNZA サイドカーを「即本線」にはしない。必要なら **漢字 NER の補助**、敬称／ひらがなは現状ルール維持。
2. **機微話題 (D)**: リリース定例は CORE だけで足りた。インシデント文の TUNING 独自語は **大半を削っても核（個人情報・漏洩・APIキー）は残る**。
3. **実施済み（A, 2026-09-13）**: `TUNING_KEYWORD_RULES` を空にし、`不正アクセス` を CORE へ。ラテン文字フレーズは大小無視マッチ。人名 stopword / `のアカウント` / few-shot は TUNING に残置。
4. **A の回帰（同一フィクスチャ）**:
   - 人名 P/R/F1: 両サンプルとも **1.0 維持**
   - 機微: リリース定例は変化なし（CORE のみで元から十分）
   - 機微: インシデントは **残る** `APIキー` / `個人情報` / `漏洩`。**消えた** `認証系` / `不正利用` / `アクセスを遮断` / `セキュリティインシデント` / `被害拡大` / `不審なアクセス` など（ハイライトは粗くなるが核は残る）
5. **次（B）**: Presidio は見送り継続。必要なら別サンプルで CORE のみの UX を目視確認してから、サイドカー是非を再判断。
